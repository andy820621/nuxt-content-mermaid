# Domain Docs

This repository uses a single-context domain documentation layout.

## Before exploring

Read the root `CONTEXT.md` and the relevant accepted contracts under `docs/specs/`. If either location does not exist, proceed without creating it.

## Vocabulary

Use the canonical terms defined in `CONTEXT.md` in issues, specs, refactor proposals, hypotheses, and tests. Do not substitute terms listed under `_Avoid_`.

## Specifications

Treat `docs/specs/` as the current source of truth for durable architecture and product contracts. A specification describes the accepted system boundary and verification scope, not the history of how the team reached it.

Decision history, alternative analysis, execution plans, blocking edges, and implementation progress belong in the configured issue tracker. Do not add ADR directories, workflow-specific plan directories, dated design notes, or task checklists to the permanent documentation tree.
